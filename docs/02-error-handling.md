# FLOWLINE — エラー処理設計

> **ステータス**: 2026-04 決定版。Phase 1 で UI を整え、Phase 2（Python 実行エンジン）
> で挙動を実装する。

---

## 背景

マルチトラック並列実行を売りにする以上、「想定外エラーが発生した時に何が
起きるか」は最初に決めないといけない。単一トラック前提なら "abort = シナリオ停止"
で済むが、複数トラックが動いていると:

- Track A でエラー → **他トラックはどうなる？**
- 中断時点で **開いているファイルや起動したアプリ** の後始末は？
- 失敗したことを **Slack / メール / ログ** で通知したい
- **「想定内のミス」** と **「本物の想定外エラー」** を区別したい

これらを汎用的に扱うため、エラー処理を **3 層モデル** で設計する。

---

## 3 層モデル

```
┌───────────────────────────────────────────┐
│ Layer 1: ブロック単位                       │
│   on_error + skipIfMissing                 │
│   「このブロック単体の想定ミス・失敗」        │
└───────────────────────────────────────────┘
                 │ 解決できない abort
                 ▼
┌───────────────────────────────────────────┐
│ Layer 2: シナリオ全体キャンセル             │
│   全トラックのワーカーに停止シグナル送信     │
│   実行中のブロックを中断                    │
└───────────────────────────────────────────┘
                 │ キャンセル完了
                 ▼
┌───────────────────────────────────────────┐
│ Layer 3: エラー処理トラック                 │
│   クリーンアップ / 通知 / エラーログ        │
│   ユーザーが自由にブロックを配置できる       │
└───────────────────────────────────────────┘
                 │
                 ▼
             シナリオ終了
```

---

## Layer 1: ブロック単位

### `onError`

| 値 | 挙動 | ログレベル |
|---|---|---|
| `abort`（デフォルト） | Layer 2 にエスカレーション。シナリオ全体を停止する | error |
| `skip` | そのブロックをスキップして次へ。警告を残す | warning |
| `ignore` | 静かに次へ。`info` ログのみ | info |
| `retry(n)` | n 回リトライ後、失敗したら `abort`（または `then` で指定した挙動） | warning→error |

`retry(n)` はオブジェクト形式も許可:

```jsonc
{ "onError": { "retry": 3, "then": "skip" } }
```

### `skipIfMissing`

**「ターゲットが見つからないのは正常」** を宣言するフラグ。`onError` とは独立:

```jsonc
{
  "type": "action",
  "nodeId": "desktop/click",
  "label": "ダイアログを閉じる",
  "params": { "method": "xpath", "value": "//Button[@Name='閉じる']" },
  "skipIfMissing": true,    // ダイアログが無ければ静かに次へ（想定内）
  "onError": "abort"         // それ以外の異常は中断（想定外）
}
```

なぜ `onError: skip` で済ませず別フィールドを設けるか:

1. **意図が JSON に明示される** — 半年後に見返したとき「なぜ skip なのか」が分かる
2. **想定内と想定外が混ざらない** — skip だと "ボタンが見つからない" と "権限エラー" が同じ扱いになる
3. **ログレベルを分けられる** — `skipIfMissing` によるスキップは `info`、`onError: skip` は `warning`

### 実装上の順序

ブロックを実行する時の判断フロー:

```
1. ターゲット存在チェック（skipIfMissing=true の場合のみ）
   ├─ 存在しない → info ログ出して次へ
   └─ 存在する → 実行へ

2. ノード実行
   ├─ 成功 → 次へ
   └─ 失敗 → onError を評価
              ├─ abort → Layer 2 へ
              ├─ skip  → warning ログ、次へ
              ├─ ignore → info ログ、次へ
              └─ retry → 再度実行
```

## Layer 2: シナリオ全体キャンセル

Layer 1 で解決できない `abort` が発火すると、Layer 2 がシナリオ全体のキャンセル
シーケンスを開始する。

### 実装方針: per-track ワーカープロセス

Electron 側は各トラックに対して独立した Python プロセスを起動している:

```
Electron (engine orchestrator)
 ├─ python_track_1.exe   ← Track 1 の全ブロック
 ├─ python_track_2.exe   ← Track 2 の全ブロック
 ├─ python_track_3.exe   ← Track 3 の全ブロック
 └─ python_error.exe     ← エラー処理用（通常は idle）
```

**トラックごとにプロセスが分離している** ので、キャンセルは単に他プロセスに
シグナルを送るだけで実現できる。

### キャンセル伝播シーケンス

1. どこかのトラックのブロックで `abort` 発火
2. そのトラックのワーカーが `{"status": "error", "escalate": "abort", ...}` を engine に送る
3. engine が他の全トラックワーカーに **SIGTERM**（Windows では `TerminateProcess`）送信
4. 5 秒待つ → まだ生きているワーカーがいれば **SIGKILL**
5. `scenario.error.*` 変数にエラーコンテキストを記録
6. Layer 3（エラー処理トラック）起動へ

### キャンセルの粒度

- **トラック単位**でキャンセル = Track A のブロックは中断されるが、Track B のブロックは触らない（すでに完了していれば変更なし）
- **実行中のブロックは強制終了** される。途中で書いたファイルや開いたアプリは **そのまま残る**（ロールバックはユーザー責任）
- キャンセル完了後は **どのトラックも再開しない**。シナリオは終了方向のみ

### なぜトラック単位のプロセス分離か

| 代替案 | 却下理由 |
|---|---|
| 単一 Python プロセス + 協調キャンセル | `time.sleep(30)` 等で待機中のブロックを止められない |
| 単一 Python プロセス + threading | Python スレッドはクリーンに kill できない |
| ノード単位のサブプロセス | 起動コスト（特に `uiautomation` の import）が重すぎる、詳細は `03-nodes.md` |

トラック単位の分離は:
- **真の並列** を実現（GIL に縛られない）
- **キャンセルが確実** に効く
- **変数干渉なし**（トラック内のノード間では共有、トラック間は engine 経由で同期）
- **クラッシュ隔離**（Track A の pyautogui クラッシュは Track B に波及しない）

## Layer 3: エラー処理トラック

シナリオに **1 本だけ存在する特別なトラック**。`abort` が発火した時にだけ
起動し、クリーンアップや通知などの後始末を行う。

### UI 上の表現

```
┌───────────────────────────────────────────┐
│ ▶ Excel処理      [起動][読込][ループ]…    │
│ ▶ メール処理     [下書][添付][待ち][送信]  │
│ ▶ ログ記録       [開始][待ち][書込]       │
├───────────────────────────────────────────┤
│ ⚠ エラー処理     [Excel閉じる][通知送信]  │ ← 赤い枠で常時ピン留め
└───────────────────────────────────────────┘
```

- 通常トラックの下に **常時表示**（空のままでも OK = 即停止のみ）
- ヘッダの色は赤系で「これは普段は走らない」ことを示す
- 通常トラックと同じブロックを配置できる
- 同期ポイントは置けない（単一トラック扱い）
- ブロックの `onError` は `abort` 不可（無限ループ防止のため `skip` に強制変換）

### 利用可能な変数

エラー処理トラック内でのみ、`scenario.error.*` が読める:

```jsonc
{
  "variables": {
    "scenario": { /* 通常通り */ },
    "error": {                        // エラー処理トラック内でのみ有効
      "trackId": "track-2",
      "blockId": "b-22",
      "blockLabel": "メール送信",
      "nodeId": "cloud/gmail_send",
      "message": "SMTP認証に失敗",
      "traceback": "...",
      "timestamp": "2026-04-11T09:30:00Z"
    }
  }
}
```

通知ブロックでこれを埋め込める:

```jsonc
{
  "nodeId": "cloud/slack_post",
  "params": {
    "channel": "#rpa-alerts",
    "text": "❌ ${scenario.error.trackId} の ${scenario.error.blockLabel} で失敗: ${scenario.error.message}"
  }
}
```

### 制約

1. **同期ポイント禁止** — 単一トラック扱い
2. **`onError: abort` 禁止** — 内部で abort を起こすと無限ループ
3. **タイムアウトあり** — デフォルト 60 秒。エラー処理自体が詰まった場合の保険
4. **ネストした errorHandler 禁止** — 1 シナリオに 1 本のみ

## 決定事項（未決定だった論点への回答）

| 論点 | 決定 | 理由 |
|---|---|---|
| エラー処理トラックは常に表示？ | **常に表示**（空でも） | 存在を忘れさせない |
| エラー処理中に発生したエラーは？ | **無視してシナリオ終了** | 無限ループ防止 |
| `retry(n)` 残数がある時の abort 要求 | **リトライを消化してから abort** | `onError` の定義通り |
| エラー処理からシナリオ本体への復帰 | **不可（必ず終了）** | MVP では単純化。後で検討 |
| 中断時の部分状態のロールバック | **ユーザー責任** | RPA では自動ロールバック不可能 |
| `scenario` 変数はトラック間で共有 | **engine 経由で同期** | 読み書きは宣言ベース、詳細は `03-nodes.md` |
| ブロック JSON の `onError` vs ノードデコレータの `on_error` | **JSON が優先** | コード触らず調整できる方が UX 優先 |
